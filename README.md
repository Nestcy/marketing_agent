# Marketing Agent (v4 — 3D Organic Content Calendar & Daily Content Generation)

Autonomous organic content platform: researches a business (Tavily +
Firecrawl), drafts a focused **3-day (3d) content calendar outline** to respect
model rate limits, and — once approved — follows through with daily cron jobs
or on-demand tasks that generate each day's **caption, a few ad copy
variants, and a ready-to-use image prompt**. No image is generated by
the platform itself — `image_prompt` is meant to be pasted into whatever
image generation tool the business already uses. This keeps the whole
pipeline runnable on just a Groq API key, with no image-provider billing
required to try it.

## The two approval gates

1. **Plan gate** — `start_campaign()` produces a LIGHTWEIGHT 3-day strategy
   outline (content pillars, tone, platform mix). One small LLM call for a
   3-day (3d) scope, preventing model rate limit exhaustion. Owner either
   `approve_plan()`s it, or `refine_plan()`s it with feedback.
2. **Day gate** — once approved, each day's content (idea, platform,
   reference-photo suggestion, caption, ad copy variants, and image prompt)
   gets generated (by daily cron or on-demand) ONLY when that day is
   actually about to be reviewed.
   - If an idea would land better with the business's own real photo than
     a generic AI-imagined one, `needs_reference_photo` is flagged and
     `notify_reference_suggested` fires — purely informational, nothing
     is blocked or regenerated on it.
   - Owner `tweak_day()`s with feedback to regenerate that one day's
     content (caption, ad copy, and/or image prompt together).
   - Owner `approve_day()`s the final draft once satisfied.

**Feedback compounds.** Every `refine_plan`/`tweak_day` call appends to
`campaign_preferences` (Postgres), and that full accumulated list gets
injected into every future generation prompt — plan regeneration AND
every day's content. Say "less product-focused" or "punchier hooks in the
ad copy" once, and future generations already reflect it.

## What runs where

- **`main.py`** — FastAPI app (`web` process)
- **`celery_app.py` + `tasks.py`** — daily cron (`worker` + `beat`)
  that generates (not publishes) each day's due draft
- **`marketing_engine.py`** — `build_graph()` is JUST the planning
  graph (research → calendar draft → stop). `generate_daily_asset()`
  is a standalone function, called once per day, NOT chained in a graph.
- **`campaign_manager.py`** — the two-gate state machine on top of the
  above, Postgres-backed
- **`chat_router.py`** — a conversational front-end (Groq tool-calling)
  over the exact same `CampaignManager` methods the REST API uses

## Deploying to Railway

Two services from this repo, each on a different `Procfile` process
type (`web`, `worker` + `beat`). Attach Postgres + Redis plugins, set
the vars from `.env.example` on all services.

## Research — direct REST, no MCP

`research_clients.py` calls Tavily's and Firecrawl's REST APIs
directly with plain API keys (`TAVILY_API_KEY`, `FIRECRAWL_API_KEY`) —
no MCP session/protocol involved.

## No image generation, by design

Earlier versions of this project called out to Gemini/DALL-E to generate
images directly, gated behind a free/paid tier. That's been removed: the
LLM now produces a detailed `image_prompt` per day instead of an image.
This drops an entire category of external billing and failure modes
(image-provider downtime, rate limits, cost-per-generation) from the
critical path, while leaving the business free to paste that prompt into
whatever image tool they already use or prefer.

## Local dev

```bash
pip install -r requirements.txt
cp .env.example .env
uvicorn main:app --reload
# separately:
celery -A celery_app worker --loglevel=info
celery -A celery_app beat --loglevel=info
```
